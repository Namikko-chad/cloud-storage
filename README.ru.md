# CloudSync

[English](README.md) · **Русский**

Синхронизация файлов между Linux, Windows и Android без управляющего сервера.
Данные хранятся в нескольких облачных хранилищах (Google Drive, Mega, S3, WebDAV,
Dropbox, OneDrive, Яндекс.Диск и другие из rclone, в том числе несколько аккаунтов
одного типа) с избыточностью Reed-Solomon k+m (m=1 — как RAID 5). Всё шифруется
и расшифровывается только на устройстве.

## Как это устроено

```
файл → чанки FastCDC (~4 МБ; мелкие файлы пакуются вместе)
     → XChaCha20-Poly1305 → Reed-Solomon k+m → по одному шарду в хранилище
```

- **Vault** (`vault.cs`) — единственный файл конфигурации: мастер-ключ, k/m,
  хранилища с доступами, устройства. Зашифрован ключом из пароля (Argon2id).
  Копия лежит в каждом хранилище, чтобы изменения (например, новое хранилище)
  доходили до других устройств.
- **Хранилище** определяется своим `id`, а не типом: два аккаунта Mega — это два
  независимых хранилища. Поле `domain` (по умолчанию — тип) — «зона отказа»: шарды
  одного блока раскладываются по разным провайдерам, а `status` предупреждает, если
  падение одного провайдера сделает файлы нечитаемыми.
- **Индекс без сервера.** Каждое устройство пишет только свой журнал операций
  (`j/<device>/<seq>`, зашифрован, копия в каждом хранилище). Дерево файлов —
  детерминированная свёртка всех операций (Lamport-часы). Параллельные правки одного
  файла дают конфликтную копию, а не потерю данных.
- **Файлы по запросу.** Список файлов есть всегда; содержимое скачивается при чтении,
  только нужные чанки. Пины (`cs pin`) держат файлы или папки на устройстве,
  `pin /` — полная локальная копия.
- **Блокировки.** Открытие файла на запись ставит lease во все хранилища. Устройство
  владеет файлом, если на большинстве хранилищ кроме его lease нет других. Пока файл
  открыт на одном устройстве, на других он открывается только на чтение.
  Lease истекает без продления (2 мин), так что пропавшее устройство не блокирует файл.
  Решение принимается, как только набрано большинство: медленное хранилище не задерживает
  открытие. После закрытия файла lease держится ещё 30 с, чтобы повторное сохранение не
  брало блокировку заново.
- **Скорость.** Все хранилища опрашиваются параллельно, к каждому — не больше 6 запросов
  одновременно. Запись в журнал возвращается, когда копии есть на m+1 хранилищах, остальные
  дописываются в фоне. Блоки файла загружаются по 4 одновременно. Чтение берёт шарды с
  хранилищ, которые отвечали быстрее (время отклика видно на экране хранилищ), и
  запрашивает ещё один шард, если хранилище отвечает намного дольше обычного. При чтении
  файла по порядку следующие 2 блока скачиваются заранее.
- **Обслуживание.** `repair` читает каждый шард (с проверкой контрольных сумм), дописывает
  потерянные, переносит их с отключённых хранилищ, перекодирует блоки после смены k/m
  (новое «поколение» шардов с другими именами) и по желанию перераспределяет данные по
  новым хранилищам. `gc` удаляет объекты, которые ни одному файлу не нужны дольше 7 дней
  (отсчёт ведёт каждое устройство само, договариваться не нужно). Журнал каждое устройство
  само упаковывает: каждые 64 сегмента — в один объект.

- **Сейф паролей.** Пароли, SSH-ключи и web3-ключи (Ethereum/EVM, Solana) в группах
  с картинкой и именем. Запись — операция `secret` в тех же журналах устройств, поэтому
  синхронизируется как дерево файлов (одновременные правки дают конфликтную копию записи).
  Внутри операции две части зашифрованы своими ключами от мастер-ключа: метаданные
  (название, логин, URL, публичный ключ, адрес) открываются для списка, а секреты (пароль,
  описание, приватный ключ, пароль ключа) — только когда открыта карточка записи. На диск
  (журналы, их локальные копии, `state.json`) попадает только шифротекст. Публичный
  SSH-ключ, отпечаток и web3-адрес ядро вычисляет из приватного ключа само.
- **2FA-коды (TOTP).** Запись вида `totp` в том же сейфе: секрет (base32 или ссылка
  `otpauth://totp/…`), алгоритм, число цифр, период и коды восстановления лежат в
  зашифрованной части. Текущие коды считает ядро (`TotpCodes`), секрет в список не уходит.
  Коды восстановления вставляются списком как есть (нумерация, колонки, заголовок и
  примечания файла отбрасываются); использованный код удаляется из записи
  (`UseRecoveryCode`) на всех устройствах.

В хранилищах лежат только объекты со случайными именами: ни имён файлов, ни размеров
отдельных файлов, ни содержимого.

## Состав

| Путь | Что |
|---|---|
| `core/crypto` | ключи, HKDF, AEAD, HMAC-имена |
| `core/vault` | файл конфигурации под паролем |
| `core/backend` | хранилища поверх rclone (+ in-memory для тестов) |
| `core/chunker` | FastCDC с ключом |
| `core/erasure` | Reed-Solomon и размещение шардов по доменам |
| `core/blob` | шифрование + RS + запись/чтение/восстановление блоков |
| `core/index` | операции, свёртка, журналы |
| `core/lock` | lease-блокировки с кворумом |
| `core/secrets` | сейф паролей: шифрование записей, вывод публичных SSH- и web3-ключей, TOTP и разбор кодов восстановления |
| `core/engine` | всё вместе: файлы, кэш, пины, синхронизация, repair |
| `core/mount` | FUSE (Linux) / WinFsp (Windows) |
| `core/rpc` | gRPC-сервис для приложения (`proto/cloudsync.proto`) |
| `cmd/cs` | CLI |
| `cmd/cloudsyncd` | десктоп-демон: gRPC + монтирование + фоновая синхронизация |
| `mobilebind` | ядро для Android (`gomobile bind` → AAR) |
| `app/` | Flutter-приложение для Linux, Windows и Android |
| `app/lib/presentation/common` | компоненты по `DESIGN_MANIFEST.md` (+ `_MOBILITY` для ширины < 768) |

## Сборка и тесты

```bash
make test          # go test ./core/...
make race          # то же с -race
make build         # builds/cs, builds/cloudsyncd (Linux, FUSE 2)
make build FUSE_TAGS=-tags=fuse3   # если есть libfuse3.so.3
make build-windows # builds/windows/*.exe (нужен WinFsp на машине пользователя)
make proto         # перегенерировать Go- и Dart-код из proto
make aar           # ядро для Android (gomobile, NDK в ~/Android/Sdk/ndk)
make app-test      # flutter analyze + flutter test
make build-linux   # приложение для Linux в builds/linux (cloudsyncd рядом)
make build-apk     # APK для Android в builds/android (сначала собирает AAR)
make app-run       # запустить приложение в режиме разработки
```

Приложение для Windows собирается на Windows: `flutter build windows` в `app/`, а
`cloudsyncd.exe` из `make build-windows` положите рядом с ним. Нужен WinFsp.

## Быстрый старт (CLI)

```bash
export CS_PASSWORD=...          # или будет спрошен
cs init -k 2 -m 1               # 2 части данных + 1 чётность: нужно ≥3 хранилищ
cs backend add -name "Mega личный" -type mega user=me@x.com pass=...
cs backend add -name "Mega рабочий" -type mega user=work@x.com pass=...
cs backend add -name "S3" -type s3 provider=AWS access_key_id=... secret_access_key=... region=eu-central-1 bucket_acl=private
cs backend add -name "Drive" -type drive token='{...}'   # token из `rclone authorize drive`
cs status
cs put ~/Documents /
cs ls -l /Documents
cs pin /Documents               # держать локально
cs get /Documents/report.pdf .
cs repair                       # дописать потерянные шарды, перенести с отключённых хранилищ
```

Обслуживание:

```bash
cs repair [-rebalance]          # проверить всё, восстановить; -rebalance — разложить по новым хранилищам
cs redundancy -k 2 -m 2         # новая схема для новых файлов, затем cs repair
cs gc                           # удалить данные, не нужные дольше 7 дней (-grace 168h)
```

Для `-type local` папка задаётся абсолютным `-root`. Неизвестные параметры отклоняются.

## Приложение

Одно Flutter-приложение на всех платформах, ядро одно и то же:

- **Linux, Windows.** Приложение — клиент демона `cloudsyncd`. Адрес и токен оно читает
  из `<config dir>/cloudsync/endpoint.json`. Если демон не запущен, приложение запускает
  его само: ищет рядом со своим бинарником, в `$CLOUDSYNCD` или в `PATH`. После
  разблокировки демон монтирует vault в `~/CloudSync`. «Открыть» в приложении открывает
  файл в этой папке, поэтому правки сохраняются, а файл на это время заблокирован.
  Закрытие файла не ждёт загрузки: файл сначала записывается в очередь на диске, потом
  загружается в фоне и пока читается из локальной копии. Если демон упадёт до конца
  загрузки, она продолжится при следующем запуске.
- **Android.** Ядро работает внутри приложения: AAR из `make aar`, foreground-сервис,
  gRPC на unix-сокете в личной папке приложения. Vault виден в системном выборе файлов
  (DocumentsProvider). Чтение идёт потоком, скачиваются только нужные части. Запись берёт
  блокировку vault и загружает файл, когда другое приложение его закрывает.
- **Экраны:** разблокировка и первая настройка (новый vault или файл с другого
  устройства); пароли (группы, карточка записи, генератор паролей, копирование с
  очисткой буфера обмена через 30 с; режим «2FA-коды» с живыми кодами и кодами
  восстановления); файлы (загрузка, открытие, «хранить на устройстве», переименование,
  удаление, кто держит файл открытым, конфликтные копии и их разрешение, поиск);
  хранилища (состояние, мастер добавления с входом через браузер для Drive, OneDrive и
  Dropbox, отключение, удаление); обслуживание (синхронизация, «держать всё на
  устройстве», проверка и восстановление, смена k/m, очистка, устройства); vault (смена
  пароля, экспорт файла vault для нового устройства, блокировка).
- **Новый vault** открывается сразу, но работает только с k+m хранилищами. До этого
  приложение показывает экран хранилищ.
- **Вход через браузер** (OAuth): ядро поднимает rclone-сервер на `127.0.0.1:53682`,
  приложение открывает ссылку. Браузер должен быть на этом же устройстве.

На новом устройстве нужен файл `vault.cs` (экспорт на экране Vault) и пароль.

Скриншоты всех экранов на 1440 и 390 px против работающего демона:
`SHOTS=/tmp/shots flutter run -d linux -t tool/screenshots.dart` (в `app/`).

## Ограничения сейчас

- Удалённые и старые версии записей сейфа остаются в журнале (зашифрованными), пока журнал
  не сворачивается в снимок. Расшифрованные пароли живут в памяти ядра и приложения, пока
  открыта карточка; Go и Dart не дают гарантированно затереть строки, а память может попасть
  в swap.
- Блокировки — «почти всегда»: офлайн-устройство их не видит; такие правки
  превращаются в конфликтные копии.
- Старые версии файлов хранятся только до GC (7 дней): истории версий в интерфейсе нет.
- Журнал упаковывается, но не сворачивается в снимок дерева: история операций растёт
  (это килобайты на тысячи правок).
- Вход через браузер работает только там, где браузер на этом же устройстве. В CLI
  OAuth-хранилищам нужен готовый `token` из `rclone authorize`.
- Windows вживую не проверялся: Go-часть кросс-компилируется, Flutter-сборку нужно
  делать на Windows.
- На Android смонтированной папки нет: файлы видны через системный выбор файлов
  (DocumentsProvider) и в самом приложении.
